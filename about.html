How I work

Three rules I keep on every build

They come from watching scripts fail quietly and handovers stall, not from a methodology deck.

Start from the manual step

The first useful artifact is a timing: how long the step takes, how often it breaks, and who fixes it. If the numbers are small, the honest answer may be not to automate it yet.

Keep the run visible

A log line per stage, a summary at the end, and a failure that names the file and the row. Silent success is as bad as a crash.

Leave a handover

README, sample data, tests and a walkthrough. A build that only I can run is not finished, however well it runs.

Questions

The things people ask first

If yours is not here, put it in the email. A short answer is cheaper than a call.

Do you work with existing code?

Yes. Most handover work starts in a repo someone else wrote. I read it first and tell you if a rewrite is cheaper than a patch, including when the answer is to leave it alone.

How do you handle data?

I work on copies, keep sample data in the repo and credentials in environment variables. Client exports do not go into version control.

What does a build cost?

Scope decides it. A single pipeline is a smaller job than a service with an API and a UI, and you get a fixed number before work starts.

Can you maintain it after handover?

If you want, yes. Otherwise the README and tests are written so your team can take it over without a call.

What do you need from me?

A sample file, the volume per week, and the person who currently does the step. The last one matters more than the first.
